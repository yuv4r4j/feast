BEST FOR
One definition of each KPI across BI, apps and AI.
Accurate text-to-SQL and governed self-serve analytics.
Consistent categories, roll-ups, navigation and tagging.

WATCH OUT
Several competing layers bring metric drift right back.
Built for star/snowflake schemas and aggregation, not inference, hierarchies or rules.
Can't say how unlike things relate, such as a loan and its collateral. That takes an ontology.
Easy to over-engineer, and it holds no data by itself.
Weak at “sum by month” aggregates; that's the semantic view's job.
Layer ⊃ View. A semantic view is one way to build a semantic layer; the layer is the goal, the view is Snowflake's native tool for it.
Taxonomy ⊂ Ontology. A taxonomy is only the is-a tree; an ontology keeps that tree and adds every other relationship plus the rules.
Ontology + data = Knowledge graph. The ontology is the schema of meaning; the graph fills it with your actual borrowers, loans and links.
3 / 3 Mental model, SQL and when to use

Mental model, real SQL, and when to reach for each

TAXONOMY The table of contents

Files every term under a broader one: Corporate under Borrower under Party. It tells you where something sits, not how it relates to anything else.

ONTOLOGY The dictionary

Takes the tree and adds relationships and rules. “A borrower is a party. A loan must have exactly one borrower.” Holds no rows.

KNOWLEDGE GRAPH The map

Who is actually connected to whom, written in the dictionary's words. Great at following paths.

SEMANTIC LAYER The contract

An agreement that “exposure” means one formula, whoever asks: a dashboard, an app or an agent.

SEMANTIC VIEW The signed copy

That contract stored as a Snowflake object, so SQL, Cortex Analyst and BI all read the same thing.

SEMANTIC VIEW · LENDING EXAMPLE 
CREATE OR REPLACE SEMANTIC VIEW risk.sem.lending_sv
  TABLES (
    loans     AS risk.core.loans     PRIMARY KEY (loan_id),
    borrowers AS risk.core.borrowers PRIMARY KEY (borrower_id)
      WITH SYNONYMS ('obligor', 'customer')
  )
  RELATIONSHIPS (
    loan_to_borrower AS loans (borrower_id) REFERENCES borrowers
  )
  FACTS (
    loans.ead AS exposure_at_default
  )
  DIMENSIONS (
    borrowers.segment   AS segment,
    loans.orig_month    AS DATE_TRUNC('month', origination_date)
  )
  METRICS (
    loans.total_ead     AS SUM(loans.ead),
    loans.loan_count    AS COUNT(loans.loan_id)
  );

-- query it like a table function
SELECT * FROM SEMANTIC_VIEW(
  risk.sem.lending_sv
  DIMENSIONS borrowers.segment
  METRICS    loans.total_ead
);

Which one do I need?

“I want the same KPI everywhere and accurate natural-language questions on my star schema.” → Start with a semantic view
“Metrics live in dbt or Looker and must serve many engines, not just Snowflake.” → A cross-tool semantic layer (OSI helps keep them in sync)
“We need one agreed list of segments and product types that rolls up cleanly.” → A taxonomy is enough
“Teams and agents disagree on what a customer, facility or default even is.” → Agree an ontology first, then generate views from it
“I need to follow chains: guarantors of guarantors, shared directors, linked collateral.” → A knowledge graph on top of the same tables
